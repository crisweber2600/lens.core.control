# Story E1-S2: Register Setup Configuration and Help Discovery

Status: ready-for-dev

## Story

As a BMad operator, I want setup to register output roots and help entries, so that Bottom-Up LENS can be discovered and configured without Lens governance side effects.

## Implementation Context

- Dev implementation target: `NextLens` at `TargetProjects/nextlens/src/NextLens`.
- Implementation writes are allowed only under `TargetProjects/nextlens/src/NextLens`.
- Runtime setup may write only BMad setup-owned config/help files in a consuming project.
- The setup skill registers module-level configuration and help discovery for `bul` commands; it must remain standalone and not call Lens lifecycle setup.

## Acceptance Criteria

1. Given `bul-setup` runs in a consuming project, when it merges configuration, then it registers `packet_output_path`, `reports_output_path`, and `default_packet_schema_version` using setup-only writes to BMad config/help files.
2. Given help discovery is inspected, when module help is loaded, then the actions `configure`, `create`, `validate`, and `verify` are available with clear arguments.
3. Given setup scripts run repeatedly, when they merge help/config entries, then output is idempotent and avoids zombie duplicate help rows.
4. Given setup is reviewed, when negative boundary checks run, then setup does not write governance mirrors, release clones, Lens lifecycle metadata, Lens constitution runtime state, or current NextLens top-down runtime files.

## Tasks / Subtasks

- [ ] Add setup assets for `module.yaml` and `module-help.csv`.
- [ ] Implement merge scripts for module config and help CSV registration using BMad setup conventions.
- [ ] Register defaults for `packet_output_path`, `reports_output_path`, and `default_packet_schema_version`.
- [ ] Add idempotency coverage for repeated setup runs.

## Dependencies And Sequencing

- Depends on: E1-S1.
- Build on the skeleton and skill folders created by E1-S1.
- This story unlocks path-guard work and create workflow routing that depend on configured output roots and help registration.

## Dev Notes

- Use defaults from architecture: `packet_output_path` as `{project-root}/docs/bottom-up-lens`, `reports_output_path` as `{project-root}/_bmad-output/bottom-up-lens`, and `default_packet_schema_version` as `bul.feature-packet.v1`.
- Keep setup config small and cross-cutting. Do not add toggles for confirmation wording, stage ordering, validation strictness, or UX copy.
- Help entries should expose `configure`, `create`, `validate`, and `verify` with output-location keys and clear arguments.

## Test / Validation Expectations

- Unit tests for config merge and help CSV merge behavior.
- Idempotency fixture for repeat setup.
- Forbidden path fixture for setup refusing non-setup output paths.

## Non-Lens Negative Acceptance Criteria

- Do not write or require `feature.yaml`, governance publish, direct governance repo writes, governance docs mirror writes, Lens branch topology, Lens constitution runtime, release clones, `.github`, Lens control-repo implementation paths, current NextLens top-down runtime modules, Landscape, Derived Graph, Salmon, promotion, adjacency, pressure, roadmap, or service/domain/program truth paths.
