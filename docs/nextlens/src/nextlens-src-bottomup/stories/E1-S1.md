# Story E1-S1: Scaffold Standalone Bottom-Up LENS Module Skeleton

Status: done

## Story

As a NextLens module maintainer, I want the Bottom-Up LENS module skeleton created in the `NextLens` repository, so that implementation starts from BMad Builder conventions rather than Lens lifecycle conventions.

## Implementation Context

- Dev implementation target: `NextLens` at `TargetProjects/nextlens/src/NextLens`.
- Implementation writes are allowed only under `TargetProjects/nextlens/src/NextLens`.
- This story creates the standalone BMad module package skeleton for Bottom-Up LENS. It must not extend Lens lifecycle behavior or reuse current NextLens top-down runtime modules.
- Runtime module writes, once future stories add them, are limited to configured `packet_output_path` and `reports_output_path` roots.

## Acceptance Criteria

1. Given the dev agent is implementing `nextlens-src-bottomup`, when it creates the initial module skeleton, then all implementation writes occur only under `TargetProjects/nextlens/src/NextLens`.
2. Given the skeleton exists, when maintainers inspect it, then it contains `.claude-plugin/marketplace.json`, `skills/bul-setup`, `skills/bul-create-packet`, `skills/bul-validate-packet`, `skills/bul-verify-receipt`, `evals`, `README.md`, and `LICENSE` placeholders or initial files.
3. Given the skeleton is reviewed, when dependencies are inspected, then it has no `feature.yaml`, governance publish flow, Lens branch topology, Lens constitution runtime, release clone dependency, or current NextLens top-down runtime dependency.
4. Given the README seed is read, when it describes the module, then it says Bottom-Up LENS is a standalone BMad module for safe packet creation, not Lens governance behavior.

## Tasks / Subtasks

- [x] Create the module root shape under `TargetProjects/nextlens/src/NextLens`.
- [x] Add `.claude-plugin/marketplace.json`, README, LICENSE, `skills/`, and `evals/` placeholders.
- [x] Seed `SKILL.md` files for `bul-setup`, `bul-create-packet`, `bul-validate-packet`, and `bul-verify-receipt` with purpose, inputs, outputs, activation boundaries, and non-Lens boundary language.
- [x] Add a structural validation placeholder that identifies the future module validation route.

## Dependencies And Sequencing

- Depends on: none.
- This is the first implementation story. It unlocks setup/config work, validation placeholders, package metadata, validator work, and create workflow routing.

- Use BMad Builder multi-skill module conventions: `.claude-plugin/marketplace.json`, `skills/<skill>/SKILL.md`, setup assets, eval folders, and concise skill routers.

- Avoid a shared helper abstraction in this story unless module validation proves the shared shape is supported.
