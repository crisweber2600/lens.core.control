# Story E3-S4: Write Packet Atomically and Emit Verified Receipt

Status: done

## Story

As an operator, I want confirmed packet creation to write one accepted packet with receipt proof, so that the safety claim is machine-verifiable.

## Implementation Context

- Dev implementation target: `NextLens` at `TargetProjects/nextlens/src/NextLens`.
- Implementation writes are allowed only under `TargetProjects/nextlens/src/NextLens`.
- Runtime create writes only packet JSON, run metadata JSON, non-effects receipt JSON, and allowed reports under configured output roots after guard, validation, confirmation, and verifier pass.
- This story is not complete unless the receipt verifier from E2-S5 proves the run before accepted success is claimed.

## Acceptance Criteria

1. Given validation, readiness reporting, path guard, confirmation, and receipt verifier pass, when packet creation writes, then it writes packet JSON, run metadata JSON, and non-effects receipt JSON only under configured allowed roots using temp files and atomic replace where practical.
2. Given post-write manifest capture runs, when changed files are compared, then only allowed packet/report outputs appear and the receipt is generated from observed changes, not prose promises.
3. Given receipt verification fails, when the workflow completes, then the accepted packet result is not claimed and the run is marked invalid.
4. Given any hard validation, path guard, confirmation, write, or verification step fails, when the flow stops, then it writes no accepted packet result and reports rollback guidance if temporary files remain.

## Tasks / Subtasks

- [ ] Compose canonical packet JSON after confirmation.
- [ ] Capture pre-write and post-write manifests for configured output roots.
- [ ] Write packet, run metadata, and receipt through temp files plus atomic replace where practical.
- [ ] Build receipt from observed writes and run metadata.
- [ ] Verify receipt before claiming accepted success.

## Dependencies And Sequencing

- Depends on: E3-S3, E2-S5.
- This story must not begin until receipt verification and false-receipt fixtures exist.
- E3-S5 adds duplicate/interruption safety after this happy-path and fail-closed write contract exists.

## Dev Notes

- Receipt claims must be built from observed changes, not from narrative expectations.
- Accepted packet success requires validation, path guard, confirmation, write, manifest capture, receipt build, and receipt verification to pass.
- If temporary files remain after failure, report rollback guidance and do not mark the packet accepted.

## Test / Validation Expectations

- Unit tests for compose, write, manifest capture, receipt build, and verifier integration.
- Integration fixture for happy path writing only allowed outputs.
- False-receipt and forbidden-changed-file tests from E2-S5 must pass before this story is accepted.
