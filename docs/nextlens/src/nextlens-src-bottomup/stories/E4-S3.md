# Story E4-S3: Add Artifact and Trigger Evals for Module Behavior

Status: ready-for-dev

## Story

As a release reviewer, I want BMad evals that prove artifact behavior and trigger boundaries, so that the module is safe to distribute.

## Implementation Context

- Dev implementation target: `NextLens` at `TargetProjects/nextlens/src/NextLens`.
- Implementation writes are allowed only under `TargetProjects/nextlens/src/NextLens`.
- Eval execution must write only allowed eval outputs/reports and configured packet/report roots.
- Trigger evals must prove Bottom-Up LENS prompts select `bul-*` skills while Lens lifecycle prompts do not activate or import Lens runtime behavior.

## Acceptance Criteria

1. Given artifact evals run on valid input, when create/validate/verify completes, then evals assert packet/receipt/run-metadata shapes and non-effects status.
2. Given artifact evals run on invalid or false-receipt fixtures, when flows execute, then evals assert fail-closed behavior and no accepted packet success.
3. Given trigger evals run on Bottom-Up LENS prompts, when skills activate, then expected `bul-*` skills are selected.
4. Given trigger evals run on Lens lifecycle prompts, when routing is evaluated, then Bottom-Up LENS skills do not activate and do not import Lens runtime behavior.

## Tasks / Subtasks

- [ ] Add artifact evals for `bul-create-packet`, `bul-validate-packet`, and `bul-verify-receipt`.
- [ ] Add trigger evals for positive Bottom-Up LENS requests.
- [ ] Add negative trigger evals for Lens lifecycle requests.
- [ ] Assert non-effects, fail-closed behavior, and no forbidden activation.

## Dependencies And Sequencing

- Depends on: E1-S3, E4-S2.
- Convert the placeholders from E1-S3 into executable evals using examples from E4-S2.
- E4-S4 depends on evals before final package validation readiness.

## Dev Notes

- Negative prompts must include feature initialization, governance publish, constitution resolution, and branch topology work.
- Artifact eval result assertions should inspect packet, receipt, run metadata, validity/readiness separation, and forbidden-write/no-Lens boundaries.
- Do not make eval success depend on governance repos, release clones, or current top-down runtime modules.

## Test / Validation Expectations

- Evals for `bul-create-packet`, `bul-validate-packet`, and `bul-verify-receipt`.
- Trigger fixture set includes bottom-up prompts and Lens lifecycle negative prompts.
- Eval result assertions include forbidden-write and no-Lens-boundary checks.

## Non-Lens Negative Acceptance Criteria

- Do not write or require `feature.yaml`, governance publish, direct governance repo writes, governance docs mirror writes, Lens branch topology, Lens constitution runtime, release clones, `.github`, Lens control-repo implementation paths, current NextLens top-down runtime modules, Landscape, Derived Graph, Salmon, promotion, adjacency, pressure, roadmap, or service/domain/program truth paths.
