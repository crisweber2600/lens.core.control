# Story E2-S3: Implement BMAD Readiness as a Separate Result

Status: done

## Story

As a Lens/BMad operator, I want packet validity and BMAD readiness reported separately, so that valid archive evidence does not imply downstream execution readiness.

## Implementation Context

- Dev implementation target: `NextLens` at `TargetProjects/nextlens/src/NextLens`.
- Implementation writes are allowed only under `TargetProjects/nextlens/src/NextLens`.
- Runtime readiness checks are read-only unless optional reports write under configured `reports_output_path`.
- Packet validity and BMAD readiness must remain independent fields in machine output and human-readable status.

## Acceptance Criteria

1. Given a valid packet has weak acceptance criteria or missing handoff context, when readiness validation runs, then the result can be `packetValid.status=pass` and `bmadReady.status=fail` with reasons.
2. Given status summaries render, when operators read them, then they use the labels `Feature packet is valid`, `Feature packet is not ready yet`, `Ready for BMAD: not yet`, and `Ready for BMAD: ready`.
3. Given readiness fails, when validation completes, then it does not invalidate packet capture solely because BMAD is not ready and does not trigger BMAD execution.
4. Given reporting/handoff consumers inspect JSON, when they read output, then validity and readiness are separate fields.

## Tasks / Subtasks

- [ ] Implement `readiness_check.py` or equivalent under the validate skill.
- [ ] Check acceptance criteria quality, constraints quality, actor clarity, provenance sufficiency, and anti-inference handoff instructions.
- [ ] Preserve `packetValid` and `bmadReady` as separate result fields.
- [ ] Add human-readable status labels exactly as specified.

## Dev Notes

- Readiness failure is not a packet validity failure unless a hard packet rule also fails.
- Do not auto-run BMAD based on readiness. This module prepares packet/readiness artifacts only.
- Preserve deterministic, keyboard-friendly, plain-language output that does not rely on color.

## Test / Validation Expectations

- Fixture proving `packetValid=pass` with `bmadReady=fail`.
- Fixture proving both pass when handoff context is sufficient.
- Snapshot tests for status labels and reasons.
